# SwiftKey dynamic.lm parser

## ALEAPP integration

`scripts/artifacts/swiftkey.py` registers three standard ALEAPP artifacts:

| Artifact | Output |
| --- | --- |
| Model Words | Terms, unigram model counts and encodings |
| Model N-grams | Sequences of order two or higher, counts and exact term boundaries |
| Model Metadata | Export status, model-level training fields, sizes and integrity hashes |

The file pattern is
`*/com.touchtype.swiftkey/files/language_models/user/dynamic.lm`. It covers
`data/data`, `data/user/0`, secondary Android users and extraction prefixes.
Beta packages and other model locations are not declared. Each row includes
its extraction-relative source path and source SHA-256. Output uses ALEAPP's
standard HTML, TSV and LAVA exporters.

`scripts/swiftkey_lm.py` provides the reader and native export decoder.
`extract_model(source, backend=None, timeout=180)` returns a dictionary containing
terms, N-gram nodes, model metadata and integrity checks. The native node list
includes unigrams; the N-gram artifact filters out order one. `decode_export(raw)`
decodes the native JSON structure without starting the backend.

Both modules use ALEAPP's normal Python dependencies. Importing them does not
start Java or download anything. Missing backend configuration is reported when
a matched model is processed; the Metadata artifact preserves an error row.

## Native backend

Extraction calls `InternalFluency.extractModelData(byte[])` in the original
ARM64 library from SwiftKey **9.10.49.20**, using Java and unidbg/Unicorn2.
`admin/swiftkey_backend/SwiftKeyNative.java` is the extraction adapter.
The library is not modified. The adapter does not provide model training.

The application must provision a backend directory containing:

```text
engine/libfluency-java-internal.so
classes/SwiftKeyNative.class
classes/SwiftKeyNative$*.class
deps/*.jar
```

Configure its absolute path through `ALEAPP_SWIFTKEY_BACKEND`. Other hosts can
pass the directory directly to `extract_model`. Runtime requires **Java 17+**;
Java resolution checks `backend/runtime/bin`, `JAVA_HOME`, then `PATH`.
Arguments are passed without a shell. The reader does not search the extraction
for executables or libraries.

`origin.json` pins the original Microsoft archive, library hash and engine
versions. `dependencies.json` pins the Maven dependencies and their hashes.
Engine binaries, JARs and compiled classes are not included in this contribution.

`setup_backend.py` prepares the directory, compiles the adapter and checks its
native export against `smoke_dynamic.lm`. Building requires **JDK 17+**.
Online preparation requires the explicit `--download` flag:

```sh
python admin/swiftkey_backend/setup_backend.py --download --output /path/to/backend
```

Offline preparation uses the same pinned archive and JARs:

```sh
python admin/swiftkey_backend/setup_backend.py --output /path/to/backend --engine-zip /path/to/SwiftKey-9.10.49.20.zip --deps-dir /path/to/jars
```

Extraction is offline after preparation. Including the Python modules in an
ALEAPP build does not provision the native backend; deployment must also supply
the configured directory and Java runtime.

## Interpretation and integrity

Words and counts are language-model values. They are not verified typing counts.
N-grams are model sequences, not reconstructed messages. `Terms JSON` preserves
term boundaries; joined text is only for display. Training timestamps describe
the whole model, not individual terms. No source app, recipient or local typing
event is inferred. The backend engine version is not the acquired app version.

The reader decodes UTF-16 code-unit slices and a depth-first N-gram tree.
Each node's pop count applies before its term ID is appended. No tokenization
or normalization is performed.

Java receives a temporary snapshot. Source and snapshot hashes are compared,
and the source hash is checked again after extraction. Source mtime is also
recorded. Invalid signatures, malformed exports, native failures, unexpected
engine versions, timeouts and source changes fail explicitly. Other matched
files continue to be processed. A successful empty export remains distinct
from a failed export.

Limits are 128 MiB input, 256 MiB native JSON, 180 seconds per native process,
1536 MiB Java heap and N-gram depth 64. Each selected artifact performs its own
export. Reading a working copy may update atime depending on its filesystem.
HTML escaping is provided by ALEAPP; TSV retains original strings, including
possible spreadsheet formulas.

## Tests

The synthetic fixture contains a binary model generated by the original engine,
its native export and an explicit corpus. It covers German, Japanese, emoji,
repeated words and shared prefixes. Expected counts are calculated independently
from the corpus: 17 terms and 37 native nodes, including 20 higher-order N-grams.
The model is not acquired device data. Automated validation covers this engine
and fixture; compatibility with other versions is not established.

```sh
python -m unittest admin/test/scripts/test_swiftkey_lm.py -v
```

Unit tests use the stored native export and real ALEAPP Context. They cover
Unicode, malformed offsets and trees, source scoping, duplicate paths, multiple
accounts, empty models, error rows, concurrent source changes and timeouts.
With `ALEAPP_SWIFTKEY_BACKEND` configured, the integration test also invokes the
original engine and rejects truncated or invalid models. Otherwise that test
is explicitly skipped. The fixture is used by this suite rather than ALEAPP's
generic case runner, which does not provision the optional backend.
